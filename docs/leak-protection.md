# 第三步：检查真实 IP 是否绕过代理

本页是客户端配置要求与验收方法。具体菜单和规则要按实际系统/客户端版本填写，首轮实机验证前不声称已经提供可直接套用的完整防泄露配置。

## 先明确要保护什么

这里检查的是：原本应该走代理的流量，是否绕过代理，从本地公网 IPv4/IPv6 直接出站。目标网站看到 VPS 地址是正常现象；手动指定直连的网站看到本地地址，也是规则的预期结果。

运营商仍知道你连接了 VPS，VPS 服务商仍掌握服务器和账户信息。账号、Cookie、浏览器指纹和主动授权的定位也可能识别你，不能用出口 IP 改变来证明匿名。

## 1. 不只开启系统代理

系统 HTTP/SOCKS 代理只影响遵循它的应用。要覆盖更多设备流量，使用客户端支持的 TUN/VPN 接管模式，核对进程排除、分应用规则、直连规则及 UDP 处理。

先明确必须代理的应用和域名，再逐项检查；TUN 开关打开不代表所有流量都已接管。`examples/client.json` 只有本地 mixed 代理，用来测试协议，不包含这里要求的策略。

## 2. DNS

- 让需要代理的域名查询按设计走代理侧 DNS，不意外回落到本地运营商解析。
- 检查浏览器自己的安全 DNS、系统 DNS 和客户端 DNS 是否有互相绕过的路径。
- DNS 测试中出现的解析器，应与配置的解析服务一致；它的 IP 不一定等于 VPS IP。
- 看到国外 DNS 不能单独证明安全，DoH 也不自动等于经过代理。严格验收还需结合客户端日志或抓包确认查询路径。

## 3. IPv6

如果本地网络有公网 IPv6，要么由代理接管 IPv6，要么在实际客户端/系统策略中阻止受保护流量从 IPv6 直连。只把节点地址写成 IPv4，并不能约束系统中的 IPv6 流量。

测试页如果显示本地运营商分配的公网 IPv6，即使 IPv4 显示 VPS，也应判定本项失败。局域网地址、链路本地地址或 mDNS 名称不等于公网 IP 泄露，要区分地址类型。

## 4. WebRTC / UDP

WebRTC 的 STUN 请求可以发现公网地址，可能与网页 HTTP 请求走不同的路径。检查实际浏览器的 WebRTC 候选地址及 UDP 出口，确认没有出现本地公网地址。

优先让相关 UDP 被正确接管。浏览器提供限制非代理 UDP 的选项时，可以结合使用；禁用 WebRTC 可能影响通话等功能，不能替代其他流量的路由保护。只看 IP 查询网站显示 VPS 不足以完成此项验收。

## 5. 断线保护

目标行为：代理失效时，受保护流量停止，不能自动转为直连。是否支持此行为取决于客户端和系统，不能假设所有 TUN 模式都自带断线保护。

分别测试节点不可达、代理进程退出、Wi-Fi/移动网络切换、休眠唤醒和系统重启。不要为测试粗暴关闭 VPS 网络或 SSH；可在本机测试配置中指向不可达端口，或使用客户端提供的可恢复故障测试方式。

## 6. 记录结果

测试前，在自己的终端记录本地直连公网 IP 作为对照；开启代理后逐项比较。完整 IP、抓包和订阅保存在私有文件，公开记录只写本地地址是否出现、客户端版本、网络类型和日期。

| 场景 | 通过标准 |
| --- | --- |
| 受保护 HTTP/HTTPS | 使用预期 VPS 出口 |
| IPv6 | 不出现本地公网 IPv6；按策略代理或阻断 |
| DNS | 查询路径符合配置，没有意外的本地解析回落 |
| WebRTC | 不暴露本地公网 IP，UDP 行为符合策略 |
| 节点/客户端故障 | 受保护流量被阻断，不转直连 |
| 切网/重启/唤醒 | 策略恢复后仍满足上述要求 |

先用同一台设备完成，再测试第二台设备。某次通过只证明当次配置和环境，没有覆盖的系统、版本和网络不能标为通过。
